# 03 · 状态变更与时序

> 状态：模型 + as-built 时序核对 · 最后核对：2026-09-17
> 作用：把"同步原理"从代码细节里抽出来，用状态变更的视角说明**为什么 docker 上不是问题、
> e2b / boxlite 上必然是问题**，以及事故发生在时序的哪一格。

## 1. 状态定义

把每个逻辑路径 `p` 的状态看成一个二元组：

```
State(p) = (S[p], X[p])
  S[p] : store 中 p 的字节内容（或不存在）
  X[p] : 沙箱 /workspace 中 p 的字节内容（或不存在）
  Base  : 沙箱诞生时从 store 复制的版本（"基线"），当前实现中隐含在 X 的初始值里
```

三个抽象事件（忽略 I/O 细节）：

| 事件 | 语义 |
|------|------|
| `HostWrite(p, v)` | 宿主文件工具写入：`S[p] ← v` |
| `SandboxWrite(p, v)` | 沙箱内 `exec` 写入：`X[p] ← v` |
| `Sync()` | 回写通道（post-exec 或 evict 触发）：把 `X` 中与 `S` 大小不同的项写入 `S` |

`Hydrate()` 是第四个事件（沙箱创建时 `X ← S`），但只在生命周期边界发生。

## 2. docker：单寄存器

在 docker 上，`S` 与 `X` **在物理上是同一份**（bind mount），因此 `X[p] ≡ S[p]` 恒成立。

| 时序 | State(p) | 说明 |
|------|----------|------|
| `Hydrate` | — | 不需要，bind mount 即共享 |
| `HostWrite(p, v2)` | `S = X = v2` | 一次写入同时作用于两份 |
| `exec` | 不变（除非脚本改这个文件） | `SandboxWrite` 与 `HostWrite` 是同一个操作 |
| `Sync()`（evict） | 不变 | 快照读回的就是 `S` 自己：`len(X[p]) == len(S[p])`，判据恒为"跳过" |

**关键**：`Sync()` 在 docker 上不是"没写"，而是**每次都真的走一遍**——walk 宿主目录、
读全部文件、逐个比大小、全部跳过。所以它既不是必要的，也不是免费的
（[01-current-implementation.md](./01-current-implementation.md) §2 的 docker 行）。

结论：docker 上没有冲突**不是因为判据聪明，而是因为在这个后端上不存在两个寄存器**。

## 3. e2b / boxlite：双寄存器 + 单向回写

```
初始：  S[p] = v1      X[p] = v1        （Hydrate）
① HostWrite(p, v2)：    S[p] = v2      X[p] = v1      ← 分叉产生，无人知晓
② exec（不碰 p）：       S[p] = v2      X[p] = v1
③ Sync()：              取快照 → v1；Stat(S[p]).Size = |v2| ≠ |v1| → Put(v1)
                        S[p] = v1      X[p] = v1      ← v2 被静默销毁
```

第 ③ 步是这个模型的全部问题：`Sync()` 的判据只看"两份大小是否相同"，
而分叉之后的两种情况它都无法区分：

| 实际情形 | 判据看到的 | 判定 | 是否正确 |
|----------|-----------|------|---------|
| 沙箱内改了 p，store 未变 | 大小不同 | 用沙箱覆盖 | ✅ 正确（这是设计意图） |
| store 内改了 p，沙箱未变 | 大小不同 | 用沙箱覆盖 | ❌ **数据丢失**（本次事故） |
| 两侧都改了 p | 大小不同 | 用沙箱覆盖 | ⚠️ 拼运气 |
| 两侧内容不同但长度相同 | `sameVersion`（大小 **且** mtime；mtime 是交付时盖进沙箱副本的戳） | 不相等则走 `equalToStore` 字节比对 ⇒ 不同即 **BLOCKED（拒绝 + 上报）** | ✅ **不再是静默漏写**：唯一仍会跳过的是"大小与 mtime 都相同但字节不同"，而那要求交付戳被伪造——沙箱内改动会改 mtime，所以它需要一个能改 mtime 的写者；T1 的字节兜底把其余情形都变成"拒绝 + 说清楚"（`internal/sandbox/lifecycle.go:744-764`，2026-09-18 的 T1 对账） |

正确的判定需要知道 `X[p]` 相对 `Base` 是否变化、`S[p]` 相对 `Base` 是否变化——
也就是需要**基线**。当前实现没有任何地方记录基线：`hydrate` 完成后，
系统对"沙箱里这份内容对应 store 的哪个版本"没有记忆。

## 4. 完整生命周期时序（e2b）

```
scope 首次被使用
  └─ Hydrate()             X ← S（把当时的 store 灌进沙箱）      ← Base 此刻确定，然后被遗忘
turn N
  ├─ HostWrite(...)        S ← 新版本，X 不动                    ← 分叉窗口开启
  ├─ exec(...)             X ← 沙箱产物
  │    └─ Sync(post-exec)  X 中与 S 大小不同的项推回 S            ← 可能覆盖 HostWrite
  └─ exec(...) 再触发一次                                          ← 又一个覆盖窗口
空闲
  └─ Sync(evict)           同上，再把 X 全量推一遍                  ← 事故常在这里收尾
     └─ Sleep() 或 Release()
        ├─ Sleep：保留 X 与 hydrated 标记 → 醒来后同一个 X 继续被回写（窗口不关闭）
        └─ Release：销毁 X → 下次 Hydrate 重建（窗口暂时关闭）
```

注意两个放大因素：

1. **Sync 的触发频率高**：每次 `exec`（仅 `RemoteWorkspace` 后端）+ 每次空闲驱逐。
   一个会话里 agent 每轮通常有多个 exec，于是"覆盖机会"是 exec 次数量级。
2. **窗口不因 sleep 关闭**：可睡眠后端保留文件系统与 `hydrated` 标记
   （[lifecycle.go](../../internal/sandbox/lifecycle.go) 第 320 行附近），
   所以旧副本可以跨越 turn、跨越分钟级等待、跨越 pod 采纳而一直存在。

## 5. 与真实会话的对齐

以 2026-09-17 事故会话为例（完整证据见 [04](./04-incident-workspace-2026-09-17.md)），
上表逐条落实为（UTC）：

| 事件 | 时间 | 状态变更 |
|------|------|---------|
| `Hydrate` | 05:25:33 | 沙箱 `iknoadnp4ho8un3yhmjr2` 建立，`X ← S`（含三个文件的早期版本） |
| `HostWrite` × N | 08:04–08:19 | `S ← 新版本`（50,282 / 6,893 / 462…），`X` 不动 |
| `Sync(evict)` | 08:09:47 | `files=2` 推回 → 覆盖 |
| `Sync(evict)` | 08:24:18 | `files=3` 推回 → 再次覆盖 |
| `HostWrite`（修复） | 08:15 / 12:07 | `S ← 55,527 / 6,893 / 462` |
| `Sync(post-exec)` | 12:05:26 | `files=1` 推回 |
| `Sync(evict)` | 12:15:17 | `files=3` 推回 → **S 最终落在旧版本（41,262 / 5,705 / 580）** |

其中 12:15:17 最值得注意：它发生在 agent 完成修复（12:07）**之后**、
且是空闲驱逐触发——与用户请求、与 agent 的任何动作都无关。

## 6. 为什么"新文件"没事

`Sync()` 对 store 里不存在的路径是可信的（它就是沙箱产物）。所以：

| 情形 | 结果 |
|------|------|
| 本会话新建、从未进入沙箱的文件 | ✅ 正确落盘（没有 `X` 可以混淆） |
| 本轮新建、且沙箱里也没有的文件 | ✅ 同上 |
| 命中 `Hydrate` 时已存在、之后被宿主工具改过的文件 | ❌ 回退（本次事故的三个文件都属于这一类） |

这解释了事故复盘时看似矛盾的现象："新写的文件全好，改过的老文件全坏"——
并不是编辑工具的问题，而是**该路径是否在沙箱里有一份旧副本**。

## 7. 触发条件的完整清单

一次静默回退同时需要：

1. 后端是分离式（`RemoteWorkspace`：e2b / boxlite）；
2. 该路径在沙箱的 `X` 中存在（来自 `Hydrate` 或沙箱内的写入）；
3. 宿主侧对该路径做过写入，且 `|S[p]| ≠ |X[p]|`；
4. 发生一次 `Sync()`（post-exec 或 evict）。

条件 1–3 决定了"有没有雷"，条件 4 只决定"什么时候炸"。因此这类缺陷的典型观察是
**延迟发生、成批发生、与用户操作无关**——正是本次事故的形态。

### 7.1 为什么"宿主写入时镜像进沙箱"关不掉这个窗口

直觉上，如果 `HostWrite` 时顺手把内容也写进 `X`，`S` 与 `X` 就一致了，条件 3 不再成立。
这条直觉在当前实现里**不成立**，原因不是镜像没写，而是它写到了另一个位置：

| | 位置 |
|---|---|
| hydrate 放下的那份 | `/workspace/sessions/<sid>/<path>`（松散会话） |
| 镜像写入的那份 | `/workspace/<path>` |

于是镜像之后仍然存在"沙箱里那个被 hydrate 的路径是旧版本"的状态，
条件 3 依然成立——只是现在多了第二个副本（详见
[01](./01-current-implementation.md) §3.5）。

这说明一个更一般的结论：**只要"逻辑路径 → 物理位置"的映射没有单一来源，
任何"写两处保持一致"的方案都只是在增加副本数量，而不是消除分叉。**

## 8. 时序上的修复着力点（供 [05](./05-remediation-plan.md) 使用）

| 着力点 | 效果 | 代价 |
|--------|------|------|
| 在 `Sync()` 入口对"共享式后端"直接短路 | 消除 docker 上的无效全量读 | 无（纯删除） |
| 把"存在且大小不同"改为**不覆盖**（保留 store，冲突副本来另存） | 立即止血；不销毁任何一侧数据 | 需要新路径约定与清理策略 |
| 记录 **Base**（沙箱 hydrate 时的 store 快照指纹），用"谁相对 Base 变了"判定 | 从机制上区分"沙箱编辑"与"宿主编辑" | 需要 scope 级持久字段（可复用 `sandbox_leases` 行） |
| 宿主写入时顺带镜像进沙箱 | 大幅降低分叉概率 | 镜像失败是常态（沙箱可能不存在），只能作为加固 |

前两项属于"不改变模型即可落地"，后两项才触及模型：这正是 [05](./05-remediation-plan.md) 分阶段的原因。
